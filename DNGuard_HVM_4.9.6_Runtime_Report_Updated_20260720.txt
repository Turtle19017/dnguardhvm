# DNGuard HVM 4.9.6 — Báo cáo hiện trạng phân tích runtime

## 1. Mục tiêu nghiên cứu

Mục tiêu cuối cùng không phải là capture hoặc giải mã từng MethodDef riêng lẻ.

Hướng chính đã được cố định:

```text
Phân tích HVM runtime dùng chung
→ xác định descriptor/table chung
→ xác định HVM compiler/translator chung
→ hook ranh giới HVM → CoreCLR JIT
→ tự động thu mọi method được runtime xử lý
→ chuẩn hóa IL, token, locals, EH và metadata
→ xây unpacker generic
```

Các token cụ thể như:

```text
0x06003B81
0x060015E2
0x0600498D
```

chỉ được dùng làm mẫu kiểm chứng cơ chế runtime. Chúng không phải pipeline unpack cuối cùng.

Nguyên tắc đã chốt:

```text
Không CaptureNext
Không Resume từng method
Không tạo queue hàng nghìn MethodDef
Không chạy một process cho mỗi token
Không yêu cầu trigger thủ công từng method
```

# 7. Descriptor và HVM method mapping

Đã xác định được layout runtime dùng chung.

## 7.1. MethodDef table

```text
MethodDef table = descriptor + 0x3A8
```

Mỗi entry chứa hai thành phần:

```text
prefix      = entry >> 20
primary_off = entry & 0xFFFFF
```

Primary record:

```text
record = descriptor + 0x3B0 + primary_off
```

## 7.2. Secondary stream

Đã chứng minh:

```text
record.d04 = secondary stream offset
```

Selector được mã hóa:

```text
encoded selector = secondary dword XOR 0x6A24E41B
```

Chuỗi correlation hiện tại:

```text
MethodDef
→ table entry
→ prefix + primary offset
→ primary record
→ record.d04
→ secondary stream
→ encoded selector
→ HVM decoder/translator
```

Đây là mapping dùng chung ở cấp runtime, không phụ thuộc vào việc capture từng method riêng biệt.

# 8. Ordinary path và helper-only path

Đã quan sát hai loại đường xử lý.

## 8.1. Ordinary path

Các method ordinary có:

```text
table hit
primary record
secondary stream hit
decoded selector
HVM translation
JIT bridge
```

Ví dụ:

```text
0x06003B81 Program.Main
0x060015E2 appUtil.get_AppDirectory
0x0600498D ZYXDNGuarder.CheckString
```

## 8.2. Helper-only path

Method:

```text
0x06005656
ZYXDNGuarder._05.CD
```

có:

```text
prefix = 0xF80
helper-only path
không có ordinary secondary stream
```

Do đó generic unpacker sẽ cần ít nhất hai handler:

```text
ordinary HVM method handler
helper-only/special-prefix handler
```

Tuy nhiên helper-only path không nên chặn việc hoàn thiện ordinary runtime collector.

# 9. Xác định đúng điểm generated IL xuất hiện

Một phát hiện quan trọng là:

```text

```

Tại checkpoint này, ba ordinary target vẫn có:

```text

```

Đây đúng bằng kích thước placeholder IL đã biết.

Điều này cho thấy DNGuard vẫn giữ hoặc restore placeholder ở vùng đó.

## 9.1. JIT bridge thật

Probe sau đó bám chuỗi:

```text
HVMRun64+0x164A9
→ HVMRun64+0xBB90
→ clrjit!compileMethod
```

Tại:

```text

```

đã thấy generated IL thật được truyền vào CoreCLR JIT.

Boundary đã được chứng minh:

```text
DNGuard HVM record/bytecode
→ HVM compiler/translator
→ generated CLR IL
→ original CoreCLR clrjit
```

        │
        ▼

        │

# 17. Correlation model của collector

Mỗi compilation cần một:

```text
compile_id
```

Ví dụ key:

```text
process id
thread id
method handle
CORINFO_METHOD_INFO pointer
IL pointer
timestamp/sequence
```

Mọi JITInfo event phải được nối với `compile_id` tương ứng.

Không nên chỉ ghép theo thread vì:

```text
nested JIT compilation
re-entrant callbacks
tiered compilation
multi-threaded JIT
```

có thể làm sai correlation.

Collector cần stack/context per thread:

```text
thread
└── active compile stack
    └── compile_id
        └── active callback stack
```

# 19. Generic unpacker offline

Sau khi corpus đủ dữ liệu, rebuild pipeline cần:

```text
1. Load dumped/original managed module.
2. Map runtime method identity về MethodDef.
3. Replace placeholder IL bằng generated IL.
4. Translate virtual tokens.
5. Reuse token thật nếu member đã tồn tại.
6. Inject MemberRef/TypeRef/TypeSpec/MethodSpec nếu cần.
7. Rebuild local StandAloneSig.
8. Rebuild EH sections.
9. Recalculate MaxStack.
10. Fix RVA/body layout.
11. Preserve resources, assembly refs và attributes.
12. Validate module load.
13. Execute regression corpus.
```

Generic unpacker cần phân biệt:

```text
metadata-representable methods
dynamic-only methods
runtime helper methods
helper-only HVM path
```

# 23. Bước tiếp theo được chỉ đạo

Bước tiếp theo gồm hai pha ngắn.

## Pha 1 — Xác nhận handle identity dùng chung

Dùng một lần để xác định cách ổn định nhất chuyển:

```text
hMethod / hClass / hField
```

sang:

```text
module + metadata token + name + signature
```

Không tiếp tục mở rộng probe theo danh sách MethodDef.

## Pha 2 — Bắt đầu Generic Runtime Collector

Collector phiên bản đầu cần tối thiểu:

```text
không có -TargetTokens
hook compileMethod boundary chung
lọc theo module/MVID
tự tạo compile_id
capture generated IL
capture resolveToken callbacks
capture runtime handles
xuất corpus nhiều method trong một lần chạy
deduplicate method
```

Sau khi collector thu được coverage ổn định, mới thêm:

```text
locals
EH
generic context
field/call semantic details
metadata injection plan
```

Đây là hướng phát triển chính thức của nhánh DNGuard HVM 4.9.6.

# 24. Cập nhật runtime-global sau báo cáo ban đầu

Phần này bổ sung các kết quả thu được sau khi hoàn tất `resolveToken` mapping và chuyển trọng tâm sang runtime-global descriptor, payload stream và translator consumer.

```text
Không capture từng method để tạo unpacker.
Không chạy một process cho mỗi MethodDef.
Token cụ thể chỉ dùng làm seed để kích hoạt và kiểm chứng cơ chế chung.
Mục tiêu cuối vẫn là generic runtime collector.
```

# 28. Payload cursor và record-data cursor

## 28.1. Payload probe v1.4.0

Probe đã xác nhận:

```text
payloadCursor = streamBase + streamOffset + 4
```

64 byte đầu của selector payload không phải CLR IL hoặc header CLR bình thường. Dữ liệu có dạng VM stream được encode.

XOR từng DWORD với:

```text
key194 = 0x6A24E41B
```

làm xuất hiện cấu trúc DWORD có quy luật, cho thấy đây là stream đã được mã hóa bằng runtime key.

## 28.2. Record-data formula v1.4.1

Đã xác minh thêm:

```text
recordType       = recordD00 & 0xFF
recordDataOffset = (recordD00 >> 8) & 0x00FFFFFF
recordDataCursor = streamBase + recordDataOffset
```

Ví dụ:

```text
0x06003B81:
recordD00       = 0x00850003
recordType      = 0x03
recordDataOffset= 0x00008500

0x060015E2:
recordD00       = 0x03AA5003
recordType      = 0x03
recordDataOffset= 0x0003AA50
```

Do đó một ordinary HVM method có ít nhất hai vùng stream liên quan:

```text
selector stream:
streamBase + streamOffset

record-data stream:
streamBase + recordDataOffset
```

Hai vùng đều có cấu trúc sau khi XOR với `key194`, nhưng hiện chưa được phép giả định một vùng luôn là bytecode cuối và vùng kia luôn là metadata. Cần tiếp tục xác định vai trò bằng translator trace.
